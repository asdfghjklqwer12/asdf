# 남은 일

규칙 엔진은 끝났다(`:domain` 테스트 86개 통과, 파이썬과 출력 동일). 여기부터가 다음이다.

---

## A. 답을 정해야 진행되는 것

### A0. 이월 상한을 얼마로 둘 것인가 — **지금 기본값이 위험하다**

이월 규칙은 붙였고 `CarryOverTest` 16개로 고정했다. 기본값은 요청받은 대로 **무제한**인데,
재어 보니 위험하다(`docs/측정-결과.md` 10절).

밀린 걸 따라잡을 여력이 없는 사용자(하루 처리 능력 = 원래 하루치)에게 무제한 이월을 걸면:

| | ○ | ✕ | 평균 유지 | 평균 이월 |
|---|---|---|---|---|
| 이월 없음 | 77.0% | 10.2% | 8.1일 | — |
| **이월 무제한** | **0.6%** | **96.6%** | **0.0일** | **112.9개** |
| 이월 1배 상한 | — | 22.8% | 1.8일 | 5.9개 |

하루 3개짜리 플랜에서 이월이 최대 288개까지 쌓이고 streak이 아예 안 돈다.

**권하는 것**: `carryOverCap = 1` (하루치의 1배까지) + 이월이 하루치를 넘는 순간
재설정 카드. 그러면 평균 유지가 4.3 → 6.4일이 되고 사용자는 월 1회만 답하면 된다.

정해주시면 기본값을 바꾸겠다.

### A1. 분량을 태스크 몇 개로 쪼갤 것인가 — **가장 급하다**

지금 도메인의 두 반쪽이 안 이어져 있다.

```
allocate()  →  { 2026-09-09: 6페이지, 2026-09-10: 6페이지, … }
settle()    ←  Subject(tasks = ?)  +  { "수학": 체크한 태스크 수 }
```

`allocate()` 는 **분량**을 내고 `settle()` 은 **태스크 개수**를 받는다. "하루 6페이지"를
체크리스트 몇 줄로 만들지가 기획 노트에 없다.

이건 취향 문제가 아니라 **판정에 직결된다.** 기획 5.2가 지적한 대로, 태스크가 1개면
전부 아니면 전무라서 △가 아예 안 나온다. 자동 분배로 만든 플랜 하나만 쓰는 사용자는
그 상태가 된다.

| 안 | 내용 | 결과 |
|---|---|---|
| A | 하루치 = 태스크 1개 ("9/9 정석 6페이지") | △가 안 나옴. 30% 규칙이 무력화 |
| B | 사용자가 태스크 크기를 정함 (예: 2페이지씩 → 3개) | △가 작동. 입력이 하나 늘어남 |
| C | 분량을 항상 3등분 | 입력은 안 늘지만 단위가 어색할 수 있음 |

**결정 없이는 자동 분배 플랜이 체크리스트가 되지 못한다.**

### A2. 48시간 복구 (기획 5.5)

기획서엔 `[결정됨]` 인데 파이썬에 구현이 없다. 옮길 게 아니라 새로 짜야 하고,
그러려면 아래가 정해져야 한다.

- "밀린 하루치를 다 했다"의 기준 — 끊긴 그날 것만? 끊긴 뒤 지난 날까지 전부?
- 복구하면 streak이 **끊기기 전 값으로 돌아가는가**, 거기서 +1인가
- "월 1회"를 어느 기준으로 세는가 — 달력 월? 30일 이동창?
- 복구된 날의 ○△✕ 표시는 무엇으로 바뀌는가 (히트맵에 어떻게 그릴지)

### A3. 결제로 조각 얻기

파이썬에 없어서 안 옮겼다. `Account.grantShard()` 가 이미 상한(프리즈 1 + 조각 5)을
지키므로 경로만 붙이면 되지만, 한 번에 몇 조각을 파는지가 안 정해져 있다.

### A4. 확인만 필요한 것 세 가지

1. **△ 간격이 4일 이상이면 영원히 안 끊긴다** (`docs/측정-결과.md` 4절).
   "주 1회 △는 무한 허용"이 의도인가?
2. **선택 과목만 있으면 전체 streak이 영원히 0이다.** 필수가 하나도 없으면 매일 휴식
   판정이라 숫자가 안 는다. 앱이 경고해야 하나?
3. **△ 비율을 사용자에게 보여줄 때** 전체 날짜 기준(13.9%)인가 학습일 기준(19.4%)인가.

### A5. 재분배 API를 더 안전하게 만들까

재분배는 **반드시 원본 계획에서 누적 완료량으로** 다시 계산해야 한다. 직전 결과 위에
또 하면 분량이 부풀려진다(무작위 600건 중 67% 어긋남, `docs/측정-결과.md` 8절).

지금은 KDoc 경고와 테스트 두 개로 막아뒀다. 그런데 `Allocation` 이 data class 라
`copy(plan = …)` 가 공짜여서 **틀린 사용법이 더 쉽다.**

→ 타입으로 막을지(예: `Redistribution.plan` 을 `Allocation` 에 못 담게), 지금처럼
문서로만 둘지 정해야 한다. 타입을 바꾸는 건 API 변경이라 그냥 하지 않았다.

### A6. 버퍼 15%를 그대로 둘까

`--args="buffer"` 로 재어봤다(`docs/측정-결과.md` 7절).

| 버퍼 | 하루 분량 | 앞쪽에서 흡수 | 중간에서 흡수 |
|---|---|---|---|
| 15% (현재) | 7p | 8일 | 6일 |
| 20% | 8p | 11일 | 9일 |

15%는 하루 1페이지를 더 내고 6~8일을 흡수한다. 기획 6.2의 "3일 밀려도 그대로"는 넉넉히
지켜지므로 **그대로 둬도 된다.** 다만 기간 후반에는 흡수력이 2일까지 떨어지니,
"후반에 밀리면 분량이 바로 늘어납니다" 안내가 필요하다.

### A7. 광고로 조각을 주는 게 맞는가 — **기획 5.5의 결정을 재검토해야 한다**

기획 5.5는 A안(광고 1회 = 조각 1개)을 "✕ 규칙이 헐거워진다"며 빼고 B안(2회 = 1개)을
택했다. **재어 보니 B안도 똑같이 헐겁다** (`docs/측정-결과.md` 9절).

| 조각을 어떻게 버나 | ✕를 막은 비율 | 평균 유지 일수 |
|---|---|---|
| 아무것도 안 함 | 0% | 8.2일 |
| 휴식일마다 자발 체크 | 55% | 16.2일 |
| **매일 광고 2편** | **93%** | **54.7일** |

광고로 버는 조각이 월 30개(프리즈 5개분)인데 ✕는 월 2.2회뿐이라, 수급이 소모의 10배가
넘는다. 조각 낭비가 월 17.7회 — 버려지는 게 얻는 것보다 많다.

비율을 더 조여도(4회당 1조각) 월 15개라 여전히 넉넉하다. 그래서 **비율 조정으로는 안 풀린다.**
판단해야 할 것은 셋 중 하나다.

1. 그대로 둔다 — "매일 광고 2편 보는 사용자"는 현실에 드물다고 보고
2. 광고 경로를 뺀다 — ✕ 방어는 휴식일 자발 체크(= 실제로 공부함)로만
3. 프리즈가 △도 막게 한다 — 그러면 프리즈가 실제로 의미 있는 방어가 된다 (규칙 변경)

> 참고: streak을 실제로 죽이는 건 ✕가 아니라 △ 3개다(2절). 프리즈는 △를 못 막는다.

## B. 규칙은 아니지만 고쳐야 할 것 — 결정 필요

### B1. 과목을 이름으로 식별한다

`settle(account, subjects, date, doneTasks)` 에서 `doneTasks` 는 `Map<과목명, Int>` 다.
같은 이름 과목이 둘이면 충돌한다. 기획 8장 데이터 모델은 `plan_id` 를 쓴다.

→ `Subject` 에 `id` 를 넣고 그걸로 식별하는 게 맞다. 파이썬도 이름을 썼기 때문에
**동작을 바꾸는 변경**이라 그냥 하지 않았다.

### B2. 정산 순서에 의존한다

`settle` 은 날짜가 증가하는 순서로 불린다고 가정한다. 과거 날짜를 나중에 정산하면
그날의 △ 창 계산은 맞지만 `overall` 은 이미 미래 날짜까지 반영돼 있어 틀어진다.

기획 10장의 "앱을 열면 미정산 날짜를 그 자리에서 계산"은 순서대로 도는 게 전제다.
호출 측 책임으로 둘지, `settle` 이 막을지 정해야 한다.

### B3. `settle` 이 매번 전체 로그를 훑는다

△ 창 계산과 멱등성 검사가 `account.logs` 전체를 스캔한다. 누적 일수에 비례하므로
1년이면 하루 365회 스캔이다. 앱에서는 감당되지만, 기획 8장이 "streak 계산은 로그
테이블만 보고 하면 되도록"이라고 한 의도에 맞추려면 저장소 계층에서 **최근 7일치만**
넘기게 잘라야 한다.

지금은 `Account.logs` 가 통째로 메모리에 있어야 하는 구조다. Room/Firebase 를 붙일 때
같이 정리하는 게 맞다.

## D. 이미 끝난 것

- `streak_sim.py` 의 `settle()` · 조각/프리즈 로직 → `:domain/streak`
- `allocation.py` 의 `allocate()` · `redistribute()` → `:domain/plan`
- 파이썬 검증 38개 → JUnit 1:1 이식, 전부 통과
- 멱등성 · `Clock` 주입 (이식 조건)
- 파이썬이 단언하지 않던 분기 32개 테스트로 고정 (제외일, `behind<=0`, 남은 날 없음,
  `base==0`, 총분량 0, △ 창 경계, 과목 프리즈 상한, 초과 체크, 필수 0개)
- 두 구현 출력 차분 검증 — 분배 19,100줄 · streak 37,604줄 완전 일치
- 30% 경계 전수 검사 — 태스크 1~300개 × 체크 0~전부, 45,450조합 완전 일치
- 버퍼 인덱스 공식 전수 검사 — 학습 가능일 2~2000일 완전 일치
- 연쇄 재분배 1,200건 차분 검증 — 완전 일치, 그 과정에서 A5 발견
- "7일 창 밖 로그는 판정에 영향 없음" 불변식을 테스트로 고정 (B3의 근거)
- 기획 5.2 숫자 재측정 + 태스크 분할 · 버퍼 비율 · 프리즈 방어율 측정 (`docs/측정-결과.md`)

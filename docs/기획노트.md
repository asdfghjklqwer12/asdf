# 학습 streak 앱 — 기획 노트

작성일: 2026-09-09 / 개인 기록용

**이 문서의 성격**: 외부 조사 없이, 대화에서 정한 전제 위에 설계를 제안한 문서다.
- `[결정됨]` = 이번 대화에서 확정한 것
- `[제안]` = 내가 제안한 설계안, 아직 확정 아님
- `[결정 필요]` = 갈림길이라 답을 정해야 하는 것
- `[확인 안 됨]` = 근거를 안 찾아본 가정

듀오링고가 실제로 어떤 streak 규칙을 쓰는지는 **[확인 안 됨]** — 이 문서의 streak 규칙은 듀오링고 복제가 아니라 이 앱을 위한 설계안이다.

---

## 1. 한 줄 컨셉

학습 플랜을 짜서 하루치 체크리스트로 쪼개주고, 하루치를 다 체크할 때마다 연속 streak이 늘어나는 Android 학습 앱.

## 2. 전제 (이번 대화에서 확정)

- `[결정됨]` 플랫폼: Android 앱
- `[결정됨]` 사용자: 불특정 다수 대상 서비스 (→ 계정·서버·동기화 필요)
- `[결정됨]` 플랜 생성: ① 직접 입력 ② 목표 → 자동 분배 ③ 당일 계획(그날 아침에 그날 할 일) — 셋 다 제공
- `[결정됨]` streak은 **과목별 + 전체** 두 층 (5.2)
- `[결정됨]` 이번 산출물: 기획 노트 (구현은 다음 단계)

## 3. 문제와 핵심 가설

**문제**: 계획은 세우는데 며칠 하다 만다. 진도표를 만들어도 밀리면 그냥 버린다.

**핵심 가설**: 하루치 학습을 완료할 때마다 연속 streak이 늘어나면 성취감이 생기고, 그 성취감이 학습을 계속하게 만든다.

- `[확인 안 됨]` "streak이 실제로 학습량·지속률을 늘린다"는 근거는 조사하지 않았다. 이 앱 전체가 이 가설 위에 서 있으므로, 나중에 자체 데이터(streak 보유자 vs 아닌 사용자의 7일/30일 잔존율)로 확인할 것.
- `[확인 안 됨]` 역효과 가능성도 조사 안 함 — streak이 끊긴 날 그대로 이탈하는 패턴. 5장 프리즈·복구 설계는 이 위험을 가정하고 넣은 것.

## 4. 핵심 개념 정의

용어를 먼저 고정해야 뒤가 안 꼬인다.

| 용어 | 정의 |
|---|---|
| **학습 플랜** | 하나의 목표 단위. 예: "수학의 정석 3개월 완주". 당일 계획도 플랜 하나다(6.3) |
| **하루치** | 특정 날짜에 배정된 학습량 |
| **태스크** | 체크리스트의 한 줄. 하루치는 태스크 1개 이상으로 구성 |
| **하루 완료** | 그날의 하루치를 완료 조건만큼 체크한 상태 |
| **과목 streak** | 한 과목(= 플랜 하나)에서 하루 완료가 연속으로 이어진 일수 |
| **전체 streak** | 계정 전체의 연속 학습 일수 |
| **○ / △(세모) / ✕** | 필수 과목 전부 완료 / 태스크 30% 이상 / 태스크 30% 미만 |
| **학습일 / 휴식일** | 플랜에서 공부하기로 지정한 요일 / 지정 안 한 날. 그날 태스크가 0개면 휴식일이다 |

## 5. streak 규칙 (이 앱의 심장, 제일 신중해야 할 부분)

### 5.1 무엇을 "하루 완료"로 볼 것인가 `[결정됨 — 전부 체크]`

그날 그 과목의 태스크를 **전부** 체크해야 하루 완료다.

- 비율 기준(80% 등)도 검토했지만 뺐다. △ 유예(5.2)가 이미 부분 달성을 흡수하는데 과목 판정까지 흐리면 이중으로 관대해져서 streak이 무의미해진다.
- 대신 부분만 한 날은 과목 로그에 `partial`로 남겨 통계에 보여준다. 끊기는 건 끊기되, 한 것도 기록은 된다.

### 5.2 과목 streak + 전체 streak `[결정됨]`

streak을 두 층으로 둔다. 듀오링고는 코스가 하나라 이 문제가 없지만, 이 앱은 "수학 + 국어 + 영어"를 같이 돌린다.

- **과목 streak**: 과목마다 따로. 그날 그 과목의 하루치를 완료하면 +1, 못 하면 **그 과목만** 0으로 끊긴다.
- **전체 streak**: 계정에 하나. 그날 결과를 ○ / △ / ✕ 로 남기고, △는 최근 7일 안에서 2번까지 봐준다.

예 — 수학·국어·영어가 모두 학습일인 날에 영어만 완료한 경우:

| 대상 | 결과 |
|---|---|
| 영어 과목 streak | 이어짐 (+1) |
| 수학 과목 streak | 거기서 끊김 (0) |
| 국어 과목 streak | 거기서 끊김 (0) |
| 전체 streak | **△**로 기록되고 이어짐, 유예 1회 소진 |

**전체 판정 기준**

| 그날 결과 | 표시 | 전체 streak |
|---|---|---|
| 그날 학습일인 필수 과목을 **전부** 완료 | ○ | +1, △ 카운트 변화 없음 |
| 그날 태스크의 **30% 이상** 했지만 전부는 아님 | △ | +1, △ 카운트 증가 |
| 그날 태스크의 **30% 미만** (0% 포함) | ✕ | 전체 프리즈로 1회 방어, 이미 썼으면 0으로 초기화 |
| 그날 학습일인 필수 과목이 없음 | 휴식 | 변화 없음 |

**△/✕는 과목이 아니라 태스크로 가른다 `[결정됨 — 시뮬레이션에서 발견]`**

처음엔 "과목을 일부만 완료 = △"로 잡았는데, 시뮬레이션을 돌려보니 구멍이 있었다. **필수 과목이 1개인 사용자는 △가 나올 수 없다** — 그 과목을 다 하거나(○) 못 하거나(✕) 둘뿐이라, △ 유예 2회를 평생 한 번도 못 쓴다. 그런데 초보 사용자는 보통 과목 하나로 시작한다.

수치로도 확인됐다 (태스크 3개/과목, 태스크 완료율 97%, 평균 streak 유지 일수). **30% 기준을 넣기 전** 측정이라 아래 5.2의 표와는 숫자가 다르다 — 여기서 볼 건 두 방식의 차이지 절대값이 아니다:

| | 필수 1개 | 필수 2개 | 필수 3개 |
|---|---|---|---|
| 과목 단위 △ | **11일** | 46일 | 28일 |
| 태스크 단위 △ | **185일** | 63일 | 28일 |

그래서 판정을 태스크 단위로 바꾼다. 과목 완료 기준(5.1의 "태스크 전부 체크")은 그대로고, **전체 판정에서만** 태스크를 센다.

**단, 하나만 하고 △를 받는 건 너무 관대하다 `[결정됨 — 30% 기준]`**

"태스크를 하나라도"로 두면 10개 중 1개(5~10%)만 체크해도 △가 된다. 그래서 **그날 배정된 태스크의 30% 이상**을 해야 △다. 못 미치면 ✕.

- 비율은 **그날 필수 과목 태스크 전체 합산** 기준이다. 수학 4개 + 영어 4개인 날에 수학 1개만 하면 1/8 = 12.5% → ✕.
- 30%는 "손은 댔다"고 인정할 만한 최소선이다. 태스크가 3개면 1개, 10개면 3개.

- 판정 대상은 **그날 학습일로 지정된 과목만**이다. 수학이 월수금 플랜이면 화요일에 수학을 안 해도 △가 아니다. 이 규칙이 없으면 요일제 플랜을 쓰는 순간 매일 △가 찍힌다.
- 필수 과목이 1개고 그 과목의 태스크도 1개뿐이면 △가 나올 수 없다(전부 아니면 전무). 이때 전체 streak = 그 과목 streak.

**△ 누적 규칙 `[결정됨]`**

- 오늘 포함 최근 7일(D-6 ~ D) 안의 △ 개수를 센다.
- △가 **3번째**로 찍히는 순간 → 전체 streak **0으로 초기화**.
- `[결정됨]` 초기화에 쓰인 △는 **소진 처리**해서 이후 카운트에서 빼야 한다. 안 그러면 초기화 직후에도 7일 창에 △ 3개가 그대로 남아, 새로 시작한 streak이 △ 한 번에 또 초기화된다. 즉 실제 판정 기준은 "최근 7일 이내 **이면서 마지막 초기화 이후**의 △ 개수".
- `[결정됨]` △인 날 전체 streak은 **+1**. 어쨌든 공부는 했으니까.

**✕ 규칙 `[결정됨]`**

- 그날 배정된 태스크의 **30%에 못 미치면** ✕ (하나도 안 한 경우 포함).
- **전체 프리즈 1개**로 1회 방어한다. 방어한 날은 streak이 **끊기지 않지만 +1도 아니다** — 숫자가 그 자리에 멈춘다. 아예 공부를 안 한 날이라 △(+1)와 차등을 둔다.
- 프리즈를 이미 쓴 상태에서 다음 ✕가 나오면 **즉시 0으로 초기화**.
- 다시 얻으려면 프리즈 조각을 모으거나 결제해야 한다(5.5). 시간이 지난다고 저절로 차오르지 않는다.
- △ 카운트와 ✕ 프리즈는 **별개 트랙**이다. 최근 7일에 △ 2개 + 프리즈로 막은 ✕ 1개면 아직 살아 있고, 여기서 △가 하나 더 나오면 △ 3번째라서 초기화된다.

**과목이 많을 때 `[결정됨 — 필수/선택 구분]`**

과목이 5개면 하나만 빠져도 △가 되는 문제가 있다.

- 과목을 만들 때 **필수 / 선택**을 고르게 하고, **전체 판정(○△✕)에는 필수 과목만** 넣는다.
- `[결정됨]` 필수 개수에 **상한을 두지 않는다**. 자기가 감당할 만큼은 본인이 정하는 게 맞다.
- 선택 과목도 **과목 streak은 정상 작동**한다. 전체에 부담을 안 줄 뿐이다.
- 이 규칙이 있으면 "과목 추가 후 며칠 유예" 같은 임시 장치는 필요 없다. 새 과목은 선택으로 시작해서 손에 익으면 필수로 올리면 된다.

**필수 과목이 늘면 확실히 어려워진다 — 완화하지 않고 알려주기로 한다 `[결정됨]`**

현재 규칙으로 측정한 결과다 (과목당 태스크 3개, 평일 학습, 평균 streak 유지 일수):

| 태스크 완료율 | 필수 1개 | 2개 | 3개 | 4개 | 5개 |
|---|---|---|---|---|---|
| 97% | 116일 | 59일 | 26일 | 16일 | 11일 |
| 93% | 39일 | 12일 | 7일 | 5일 | 4일 |
| 88% | 14일 | 5일 | 4일 | 3일 | 2일 |

△가 찍히는 비율도 같이 오른다 — 태스크 완료율 93%에서 필수 1개는 14.6%, 3개는 35.1%, 5개는 48.1%.

완화안(△ 상한을 "2 + 필수 과목 수"로)을 넣어 측정해봤더니 **반대로 과하게 헐거워졌다** — 필수 4~5개에서 200일을 돌려도 거의 초기화가 안 된다. △를 개수로 자르는 이상, 과목 수가 만드는 증가폭을 상한 조정으로 맞추기는 어렵다.

그래서 **완화 장치를 넣지 않는다.** 필수를 3개 넣는다는 건 "매일 세 과목을 다 끝내겠다"는 선언이고, 그게 어려운 건 규칙의 결함이 아니라 선택의 결과다. 앱이 할 일은 규칙을 무르게 만드는 게 아니라 **그 선택의 무게를 미리 알려주는 것**이다.

- 플랜을 필수로 지정할 때: "필수가 3개가 됩니다. 세 과목을 매일 다 끝내야 ○예요."
- 기록 화면에서 △가 잦으면: "최근 2주 중 8일이 세모예요. 한 과목을 선택으로 내려볼까요?"

### 5.3 하루의 경계

- `[결정됨]` 하루 마감 시각을 사용자가 설정 (기본 **새벽 3시**). 자정 기준이면 밤 12시 넘겨 공부한 사람의 streak이 억울하게 끊긴다.
- `[결정됨]` 기준 시각은 **서버 시각 + 사용자 타임존**. 기기 시계를 바꿔서 streak을 늘리는 어뷰징을 막기 위함.
- `[결정됨]` 해외 이동 등으로 기기 타임존이 바뀌어도 **계정에 저장된 타임존을 그대로 쓴다**. 설정에서 수동으로 바꿀 때만 반영. 기기 값을 따라가면 시계 조작 방지가 무의미해지고, 하루 경계가 움직여 streak이 이상하게 끊긴다.

### 5.4 휴식일

- `[결정됨]` 플랜에서 학습일로 지정 안 한 날은 **중립** 처리 — streak이 끊기지도, 늘지도 않는다. (주 5일 플랜이면 주말에 안 해도 유지)
- `[결정됨]` 휴식일에 자발적으로 공부하면 streak을 늘려주는 게 아니라 **프리즈 조각 1개**를 준다(5.5). streak을 늘려주면 "휴식일을 많이 잡아두는 쪽"이 유리해지는 이상한 유인이 생긴다.
- **휴식일에는 체크할 태스크가 없다** — 그날은 배정된 게 없으니까. 그래서 "자발적으로 체크"는 **다음 학습일의 하루치를 당겨와서 하는 것**으로 정의한다 `[결정됨]`. 홈에 "오늘 미리 해둘까요?" 버튼을 두고, 누르면 다음 학습일 태스크가 오늘 체크리스트로 올라온다. 다 하면 조각 1개를 주고 그 학습일은 완료 처리된다. 진도도 나가고 조각도 받는다.
- `[결정됨]` 과목마다 휴식 요일이 다르면 전체 판정은 **그날 학습일인 과목만** 본다(5.2). 모든 과목이 휴식일인 날은 전체도 휴식 — ○도 △도 아니고 그냥 넘어간다.

### 5.5 프리즈와 복구

프리즈는 두 종류다. 헷갈리지 않게 이름을 나눠 쓴다.

| | 방어 대상 | 보유 | 얻는 법 |
|---|---|---|---|
| **과목 프리즈** | 그 과목을 **완료 못 한 날** → 과목 streak 유지 | 최대 2개 | 그 과목 7일 연속 완료 시 1개 |
| **전체 프리즈** | ✕인 날 → 전체 streak 유지 (5.2) | 최대 1개 | **프리즈 조각 6개**를 모으거나 결제 |

**프리즈 조각 `[결정됨]`**

전체 프리즈는 시간이 지나면 저절로 차오르는 게 아니라, **뭔가를 해야** 얻는다. 가만히 있으면 안 생긴다는 게 요점이다.

조각 6개 = 전체 프리즈 1개. 얻는 경로는 셋:

| 경로 | 지급 | 제한 |
|---|---|---|
| 휴식일에 자발적으로 체크 | 1조각 | 주 3조각까지 `[제안]` |
| **보상형 광고 2회** 시청 | 1조각 | 광고는 하루 2회까지 → 하루 최대 1조각 |
| 인앱결제 | 조각 묶음 또는 프리즈 1개 | — |

**광고 길이를 60초로 못 박는 건 안 된다** — AdMob 보상형 광고는 보상까지의 카운트다운이 **5~30초**이고, 그 길이는 **광고 소재가 정한다**. 개발자가 지정하는 설정이 아니다 [출처: Google AdMob Help — Overview of rewarded ad units].

`[결정됨 — B안]` 그래서 "길게 보게 해서 귀찮게 만든다"는 원래 의도를 길이로는 구현할 수 없다. 횟수로 옮긴다:

| 안 | 내용 | 광고만으로 프리즈 1개까지 |
|---|---|---|
| A | 광고 1회 = 1조각, 하루 2회 | 3일 |
| **B (채택)** | **광고 2회 = 1조각, 하루 2회** | **6일** |

A는 사흘에 한 번씩 ✕를 내도 계속 막히는 상태가 되어 ✕ 규칙이 헐거워진다. B는 광고를 봐도 하루에 조각 1개가 상한이라, 프리즈 하나를 얻으려면 엿새 동안 매일 광고 2편을 봐야 한다. 그 정도면 "그냥 공부하고 말지"가 된다.
`[확인 안 됨]` 다른 광고 네트워크(Unity Ads, ironSource 등)에 더 긴 보상형 광고가 있는지는 안 찾아봤다.

- 과목 프리즈는 그 과목을 **완료하지 못한 날**에 쓰인다. 부분만 한 날도 과목 기준으로는 미완료(5.1)라 프리즈가 소모된다.
- **보유 상한 1개는 결제로도 못 넘는다.** 이게 핵심 안전장치다. 돈으로 프리즈를 계속 사서 영원히 안 끊기게 만들 수 있으면 streak이라는 숫자 자체가 의미를 잃는다.
- **조각도 상한이 있다 — 프리즈를 들고 있는 동안은 5개까지** `[결정됨]`. 조각에 상한이 없으면 미리 잔뜩 사두고 프리즈를 쓰는 족족 채울 수 있어서, "보유 1개" 안전장치가 보유량이 아니라 **재충전 속도** 쪽에서 뚫린다. 최대 비축량은 **프리즈 1개 + 조각 5개**다.
- 그래서 "대기 상태"는 존재하지 않는다. 프리즈를 쓰면 조각이 5개 차 있으니 그다음 1개만 얻어도 바로 다시 채워진다.
- 조각을 광고·결제로 얻게 한 의도: 광고를 보기 싫거나 돈을 쓰기 싫어서라도 그날 공부를 하게 만드는 것.
- 둘 다 **소진 시 자동 사용**. 사용자가 직접 고르게 하면 "아껴야 하나" 하는 판단 부담만 생긴다.
- `[결정됨]` 과목 프리즈가 어떤 과목을 지켜준 날, **전체 판정에서는 그 과목을 완료로 치지 않는다**. 실제로 공부한 게 아니니까. 다른 과목을 했으면 △, 아무것도 안 했으면 ✕다.
- `[결정됨]` **복구**: 끊긴 뒤 **48시간 이내**에 밀린 하루치를 다 하면 1회 복구. 과목·전체 둘 다 대상. **무료, 월 1회**. streak 복구를 유료로 걸면 앱에 대한 신뢰가 먼저 깨진다고 봤다.

## 6. 플랜 생성

### 6.1 방식 ① 직접 입력

- 플랜 이름, 과목
- 날짜별로 태스크를 직접 추가 / 요일 반복 태스크 ("월수금 영단어 30개")

### 6.2 방식 ② 목표 입력 → 자동 분배 `[결정됨]`

**입력**
- 총 분량 + 단위 (예: 480페이지 / 300문제 / 45강)
- 시작일, 목표일
- 학습 요일 (예: 월~금)
- 하루 최대 분량 (선택)
- 제외일 (시험 기간, 여행 등)

**계산**
```
학습가능일 D = (시작일~목표일 사이의 지정 요일 수) - 제외일 수
버퍼일 B = ceil(D × 0.15)        # 밀림 흡수용 예비일 [제안]
분배일 N = D - B
기본 하루치 = floor(총분량 / N)
나머지 R = 총분량 - (기본 하루치 × N)  → 앞쪽 R일에 +1씩
```
**버퍼일이 뭐냐면** — 학습 가능일 전부에 분량을 꽉 채워 넣으면, 하루라도 밀렸을 때 그 밀린 몫을 넣을 자리가 없다. 그래서 학습 가능일의 15%를 **일부러 비워두고** 나머지 85%에만 분량을 배분한다.

예: 480페이지를 100일(학습 가능일) 안에 끝낸다고 하면
- 버퍼 없이: 100일 × 4.8페이지 → 하루라도 빠지면 남은 날에 얹어야 해서 분량이 계속 늘어난다
- 버퍼 15%: 15일을 비우고 85일 × 5.6페이지 → 3일 밀려도 비워둔 15일 중 3일로 흘러들어가고, 하루 분량은 그대로다

즉 버퍼는 "밀릴 걸 미리 계산에 넣어두는 여유분"이다. 하루 분량이 조금 늘어나는 대신 플랜이 안 무너진다. `[제안]` 15%가 적절한지는 실제로 써보고 조정.

**검증에서 나온 수정 2가지 `[결정됨 — 코드 반영 완료]`**

위 계산식을 그대로 코드로 옮겨 돌려보니 두 군데가 잘못돼 있었다. `allocation.py`에 고쳐 넣고 검증 통과했다.

1. **버퍼일을 뒤에 몰지 말고 흩어놓는다.** 원래 계산식은 앞 N일에 분량을 채우고 나머지를 버퍼로 두는데, 그러면 버퍼가 전부 기간 끝으로 간다. 480페이지 / 9월 9일~12월 31일 예시에서 버퍼 13일이 **12월 15일~31일에 통째로 몰렸다**. 9월에 밀렸는데 흡수해줄 여유일이 12월에 있는 셈이고, 사용자 화면엔 마지막 3주가 텅 빈 것처럼 보인다.
   → 버퍼 위치를 `int((k + 0.5) × D / B)` 로 잡아 **학습일 사이에 균등하게 흩는다**. 같은 예시에서 버퍼 간격이 8~10일(평균 8.8일)로 퍼져서, 밀린 걸 그 주 안에서 흡수한다.

2. **분량 0인 날은 학습일이 아니라 휴식일이다.** 총분량이 배분일 수보다 적으면(예: 5강짜리를 3개월에) 분량 0인 날이 학습일로 남는다. 그날은 체크할 태스크가 없는데 필수 과목의 학습일이라 **자동으로 ✕가 찍힌다.**
   → 분량이 0인 날은 휴식일로 분류해서 내보낸다. 5.2의 "그날 학습일인 필수 과목이 없으면 휴식"으로 자연히 넘어가고, 자동 ✕가 안 찍힌다.

**버퍼일도 결국 휴식일이다.** 버퍼일은 분량이 0인 날이므로 위 규칙에 따라 그대로 휴식일이 된다 — 코드에서도 두 목록이 완전히 겹친다. 그래서 필수 과목이 하나뿐인 사용자는 **8~10일에 한 번씩 전체 streak이 늘지 않고 멈추는 날**이 생긴다. 끊기는 건 아니고 그날만 중립이다. 82일짜리 플랜이면 최대 streak이 82가 아니라 69다. 이건 결함이 아니라 "쉬는 날은 안 센다"는 규칙의 당연한 결과이므로 그대로 둔다.

**막아야 하는 입력** — 검증에서 예외 처리를 넣은 것들:
- 학습 가능일 0일 (요일 선택과 기간이 안 맞음) → 저장 불가
- 학습 가능일 1일 (버퍼가 전부 먹어서 배분할 날이 0) → 저장 불가

- 하루치가 "하루 최대 분량"을 넘으면 → **경고 + 목표일 연장 제안**. 지키지 못할 플랜을 만들게 두지 않는 게 핵심.
- 결과는 **캘린더 미리보기**로 보여주고, 저장 전에 손으로 고칠 수 있어야 한다.

**재분배** (밀렸을 때)
- 미완료 분량을 남은 학습일에 다시 펼친다. 버퍼일이 먼저 소모된다.
- 재분배 후에도 하루 최대 분량을 넘으면 → 목표일 연장 / 분량 축소 중 선택하게 한다.
- `[결정됨]` **자동 계산 + 확인**. 밀린 뒤 앱을 열면 "3일 밀렸어요, 이렇게 조정할까요?" 카드가 뜨고 사용자가 [조정 / 목표일 연장 / 분량 축소] 중 고른다. 말없이 바꾸면 사용자가 자기 플랜을 통제하지 못한다고 느낀다.

### 6.3 방식 ③ 당일 계획 `[결정됨]`

긴 플랜을 짜는 학생만 있는 게 아니다. **그날 아침에 그날 할 걸 적는** 방식이 오히려 더 흔하다. 이 방식을 따로 지원한다. 판정 메커니즘은 기간 플랜과 완전히 동일하다 — ○△✕, 30% 기준, △ 유예, 프리즈 전부 그대로.

**구조**: 당일 계획은 **"오늘 계획"이라는 상시 과목 하나**다. 매일 새 과목을 만드는 게 아니라, 과목 하나를 두고 그날그날 태스크를 채운다. 이렇게 해야 **과목 streak이 이어진다** — 매일 새 과목이면 streak이 영원히 1일에서 멈춘다.

- 홈에서 "+ 오늘 할 일"로 태스크를 추가한다. 요일 설정도, 분량 계산도 없다.
- 필수/선택은 다른 과목과 똑같이 고를 수 있다.
- 기간 플랜과 같이 돌아간다. 둘 다 필수면 그날 태스크가 합산되어 30% 판정을 받는다.

**함정 — 계획을 안 넣은 날 `[결정됨]`**

당일 계획 과목은 "그날 태스크가 0개"인 날이 생긴다. 이걸 그냥 두면 **계획을 안 짠 날마다 태스크 0개짜리 학습일이 되어 자동으로 ✕가 찍힌다.** 6.2의 "분량 0인 날" 문제와 같은 모양이다.

→ **태스크를 하나도 안 넣은 날은 그 과목의 휴식일**이다. streak이 끊기지도, 늘지도 않는다.

여기서 "계획을 안 짜면 페널티가 없으니 안 짜는 게 유리하지 않냐"는 반론이 가능한데, 실제로는 균형이 맞는다. 휴식일은 **중립**이라 그날은 숫자가 안 늘어난다. 계획을 안 짜면 streak이 유지될 뿐 자라지 않으니, 성취감이라는 보상 자체가 없다. 벌을 주는 대신 보상을 안 주는 쪽으로 처리하는 게 이 앱의 다른 규칙(휴식일, 버퍼일)과도 일관된다.

**어뷰징 여지 — 그냥 둔다 `[결정됨]`**

마감 직전에 "이미 한 것"만 적어 넣으면 매일 ○를 받을 수 있다. 태스크 삭제도 자유라 많이 적고 지워도 된다. 막을 수단은 있지만(추가 후 삭제 금지, 추가 시각 기록 등) 넣지 않는다 — 12장에서 "공부 안 하고 체크만 하는 자기기만은 가정하지 않는다"고 정했고, 당일 계획은 그 판단이 가장 직접적으로 적용되는 곳이다. 자기를 속이는 건 사용자 몫이다.

### 6.4 방식 ④ 템플릿 `[결정됨 — MVP 제외]`

미리 짜인 플랜(수능 과목별, 자격증, 어학)을 고르는 방식. MVP의 목적은 streak 규칙 검증이라 여기에 콘텐츠 제작 비용을 쓸 단계가 아니다. 11장 참고.

`[확인 안 됨]` "그날그날 계획을 짜는 학생이 더 많다"는 건 사용자가 관찰한 바이고, 비율을 조사하지는 않았다.

## 7. 화면 구성 `[결정됨]`

1. **온보딩** — 무엇을 공부할지 → 목표·기간 입력 → 첫 플랜 생성까지 한 번에
2. **홈(오늘)** — 상단에 **전체 streak** 숫자(제일 크게) + 이번 △ 게이지("△ 2/2 — 하나 더 나면 초기화"), 그 아래 **필수 과목** 체크리스트(각 과목 streak 배지) → 구분선 → **선택 과목** 체크리스트, 진행률 링, 남은 일수. 당일 계획 과목에는 **"+ 오늘 할 일"** 버튼이 붙는다 (6.3)
3. **플랜 만들기** — 방식 선택(직접 입력 / 자동 분배 / **당일 계획**) → 입력 → **필수/선택 지정** → 캘린더 미리보기 → 저장
4. **플랜 상세** — 캘린더(완료/부분/미완료 색), 전체 진행률, 재분배 버튼, 태스크 편집
5. **기록** — ○/△/✕ 3단계 히트맵, 전체 현재·최장 streak, 과목별 streak 목록, 요일별 완료율, 총 학습일
6. **설정** — 알림 시각, 하루 마감 시각, 계정, 타임존

체크하는 순간의 피드백(애니메이션·소리·streak 숫자 증가)이 이 앱의 핵심 경험이므로, 여기에 공을 들일 것.

△가 2번 찬 상태는 **끊기기 전에** 사용자가 알아야 한다. 홈 게이지 + 그날 알림 문구를 "오늘 안 하면 연속 초기화" 쪽으로 바꿔서 경고한다.

- `Task.done_at`은 **서버 시각**으로 기록.
- `DayLog` / `OverallLog`는 마감 시각에 서버 배치가 확정(closed_at). 클라이언트가 판정하면 어뷰징 여지가 생긴다.
- streak 계산은 로그 테이블만 보고 하면 되도록 만든다 (Task를 매번 훑지 않게).
- △ 카운트 쿼리: `OverallLog에서 mark='partial' AND date BETWEEN D-6 AND D AND consumed_at IS NULL` 의 개수. 초기화가 일어나면 그 창의 △들에 `consumed_at`을 찍는다.
- `subjects_due` / `subjects_done`을 로그에 박아두면 나중에 규칙(예: 80% 기준)을 바꿔도 과거 기록을 다시 계산할 수 있다.

## 10. 기술 스택 `[결정됨]`

**클라이언트 (Android)**
- Kotlin + Jetpack Compose
- Room (로컬 캐시 — 오프라인에서도 체크는 되어야 함)
- WorkManager (알림 예약, 동기화 재시도)
- DataStore (설정)

**서버** — 불특정 다수 서비스라 필수 `[결정됨 — Firebase]`
- Firebase Auth + Firestore + Cloud Functions로 MVP를 낸다. 서버 코드를 최소로 줄이고 streak 규칙 검증에 시간을 쓰기 위함. 사용자가 붙으면 재검토하되, 데이터 모델을 관계형으로 짜뒀으니 이전 가능하게 유지.
- **정산 방식**: 타임존마다 크론을 24개 돌리는 건 과하다. ① 사용자가 앱을 열면 미정산 날짜를 서버 시각 기준으로 그 자리에서 계산 ② 알림 발송용으로 하루 1회 배치. 앱을 며칠 안 열어도 다음 접속 때 밀린 날이 한 번에 채워진다.
- 정산 함수는 **멱등**하게 짠다. 같은 날짜를 두 번 계산해도 streak이 두 번 오르면 안 된다 (`OverallLog.closed_at` 있으면 건너뛰기).

**알림**: FCM
**오프라인**: 체크는 로컬에 먼저 기록하고 온라인 시 동기화. 충돌 시 `done_at`이 이른 쪽 우선.

## 11. 범위

**MVP가 뭐냐면** — Minimum Viable Product, "최소 기능 제품". 앱을 처음부터 다 만들지 않고, **이 아이디어가 말이 되는지 확인할 수 있는 최소한의 버전**만 먼저 만드는 것이다.

이 앱에서 확인해야 할 질문은 하나다: **"streak이 실제로 사람을 계속 공부하게 만드는가."** 3장의 핵심 가설이 그거니까.

그래서 판단 기준이 단순해진다 — 그 질문에 답하는 데 필요하면 넣고, 없어도 답할 수 있으면 뺀다. 템플릿이 없어도 streak이 사람을 붙잡는지는 확인할 수 있으니 뺐고, 친구 랭킹도 마찬가지다. 반대로 프리즈·복구는 "끊긴 날 이탈"이라는 가장 큰 위험을 직접 건드리니까 넣었다.

**MVP에 넣을 것**
- 소셜 로그인 (구글)
- 플랜 생성 (직접 입력 + 자동 분배 + 당일 계획), 과목 필수/선택 구분
- 오늘 체크리스트 + 체크 피드백
- 과목 streak + 전체 streak (○/△/✕ 판정, △ 7일 2회 유예, 프리즈, 조각, 복구)
- 보상형 광고 + 인앱결제 (프리즈 조각) `[결정됨]` — 프리즈를 얻는 경로 자체라서 MVP에서 뺄 수 없다
- 밀렸을 때 재분배
- 알림 1회 (사용자 지정 시각)
- 기록 화면 (히트맵 + 최장 streak)

**나중에**
- 템플릿 / 플랜 공유 `[결정됨 — MVP 제외]` MVP의 목적은 streak 규칙이 실제로 사람을 붙잡는지 확인하는 것이고, 템플릿은 콘텐츠 제작 비용만 크고 그 검증과 무관하다
- 친구·랭킹·리그
- 복습 주기 자동 삽입 (에빙하우스식 3일·7일 뒤 복습 태스크)
- 홈 화면 위젯
- 학습 타이머 연동
- 프리미엄 구독 (상세 통계, 위젯 테마 등) — 프리즈 조각 결제와는 별개로 나중에 검토

### 만 14세 미만이 제일 중요하다

학습 앱이라 중·고등학생, 초등학생이 들어올 가능성이 높다. 그런데 한국 개인정보 보호법은 만 14세 미만을 따로 다룬다.

- 아동에게 고지할 때는 **이해하기 쉬운 양식과 알기 쉬운 언어**를 써야 한다 — 같은 조 [출처: 법무법인 비트]
- 위반 시 제재: 5년 이하 징역 또는 5천만원 이하 벌금(제71조 제3호), 전체 매출액 3% 범위 내 과징금(제64조의2 제1항 제2호) [출처: 법무법인 비트]

|---|---|---|
| A | 가입 시 나이를 묻고 **만 14세 미만은 가입 차단** | 구현이 제일 간단. 대신 초등·중1 사용자를 통째로 포기 |
| B | 만 14세 미만은 **보호자 동의 절차**를 붙임 | 사용자층을 안 버림. 대신 동의 확인 수단(보호자 휴대폰 인증 등)을 붙여야 해서 개발·비용 부담이 큼 |

**A로 간다.** 검증할 질문은 "streak이 사람을 붙잡는가"지 "초등학생도 쓸 수 있는가"가 아니다. B는 서비스가 자리 잡은 뒤에 붙여도 된다.

구현할 것: 가입 화면에서 생년월일(또는 "만 14세 이상입니까") 확인 → 미만이면 가입 차단 + 안내 문구. 나이 자체를 저장할 필요는 없다. 통과 여부만 남기면 수집 항목이 줄어든다.

### 그 외에 반드시 해야 하는 것

- **개인정보처리방침 작성·게시.** 구글 플레이는 데이터 보안 양식을 채우려면 개인정보처리방침이 필수다 [출처: Play Console 고객센터]
- **구글 플레이 데이터 보안 양식 제출.** 프로덕션뿐 아니라 비공개·공개 테스트 트랙에 올려도 작성해야 한다(내부 테스트는 제외). 수집·공유 여부, 전송 중 암호화 여부, 삭제 요청 수단 제공 여부, 데이터 유형별 수집 목적과 필수/선택 구분을 선언해야 한다 [출처: Play Console 고객센터]
- **수집 항목 최소화.** 이 앱에 실제로 필요한 건 계정 식별자와 타임존 정도다. 이름·전화번호·생년월일은 안 받아도 굴러간다. 적게 받을수록 의무도 줄어든다.
- **삭제 수단.** 계정 삭제 기능을 앱 안에 넣는다. 데이터 보안 양식에서 묻는 항목이기도 하다.

`[확인 안 됨]` 구글 플레이의 어린이 대상 앱(Families 정책) 요건, 인앱결제를 미성년자에게 제공할 때의 추가 요건은 확인하지 않았다. 결제를 붙이기 전에 따로 봐야 한다.

## 16. 언제 Claude Code로 넘어가나

- **지금 단계(기획·규칙 설계·목업)**는 여기서 하는 게 맞다. 코드베이스가 아직 없다.
- **streak 시뮬레이션**(14장 2번)도 여기서 된다. 파이썬 스크립트 하나면 되고, 앱 코드가 아니다.
- **Android Studio 프로젝트를 만든 다음부터** Claude Code가 의미 있다. Claude Code는 실제 프로젝트 폴더를 직접 읽고 여러 파일을 동시에 고치는 도구라, 고칠 파일이 있어야 쓸모가 생긴다. Compose 화면을 짜고, Room 스키마를 만들고, 에뮬레이터로 돌려보는 단계가 그때다.
- 정리하면 **"프로젝트 폴더가 생기는 순간"**이 전환점이다.
